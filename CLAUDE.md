# Питомец Финни

Android-приложение для хакатона по ТЗ №6 Департамента финансов города Москвы:
игра про финансовую грамотность для детей 7–11 лет. Kotlin, Jetpack Compose,
Hilt, Room, контент-пак в `app/src/main/assets/content/v1/`.

## Текущая работа

Работаем строго по `docs/PLAN_V3.md`:
- порядок коммитов — раздел 7;
- игровые правила и числа экономики — раздел 3;
- эталонные числа для проверки экранов и тестов — раздел 4;
- схемы экранов — раздел 8.

Прототипы совы и экранов — `docs/prototypes/` (см. там `README.md`).
Архитектурные решения — `docs/ARCHITECTURE_DECISIONS.md`.

## Коммиты и пуш

- Один коммит = одно законченное изменение.
- После КАЖДОГО коммита остановись и дождись моего подтверждения.
  Следующий коммит — только после моего «дальше». Коммиты не копить.
- `git push` НИКОГДА не выполняй. Пушу только я сам.
- Объём: до ~300 строк боевого кода на коммит, тесты не считаются.
  Больше — разбей на несколько коммитов.
- Сообщение коммита на русском, в стиле истории: «Область: что сделано + тесты».
- Не добавляй Co-Authored-By.

## После каждого коммита — выжимка на 5–10 строк

- что сделано, простыми словами
- какие технологии или приёмы применены впервые в проекте
- почему выбрано так, а не иначе
- что сломается, если сделать наоборот

## Строго по ТЗ

- Делаем только то, что требует ТЗ или о чём я прямо попросил.
- Никаких функций «на будущее» и «заодно».
- Новое игровое правило или экран — сначала предложи и дождись «ок».
- Перед крупным изменением покажи план по файлам и дождись «ок».
- Решения по архитектуре — в docs/ARCHITECTURE_DECISIONS.md, работаем по ним.

## Просто, без слопа

- Самое простое решение, которое закрывает требование.
- Нестандартное (транзакции, синхронизация, дженерики с вариантностью и т.п.)
  — только если без него сломается логика. В выжимке отдельной строкой
  «ВНИМАНИЕ:» объясни, зачем оно и что будет без него.
- Не создавай новую абстракцию, если подходит существующий класс или компонент.
- Без мёртвого кода, неиспользуемых параметров и дублирования.
- Новые библиотеки — только с объяснением, зачем она и что без неё.

## Архитектура и качество

- Домен без Android-зависимостей.
- К каждому изменению логики — тесты.
- Контент (тексты, фразы питомца, числа экономики) — в JSON контент-пака, не в коде.
- Анимации и звуки отключаются существующей настройкой доступности.
- Комментарии объясняют ПОЧЕМУ, а не ЧТО.

## Тесты при разработке

- На каждый коммит запускай только unit-тесты: ./gradlew testDebugUnitTest
- Инструментальные тесты (androidTest) запускай только по моей просьбе
  и перед релизом.
- Существующие тесты не удаляй.
- Для экранов, которые сейчас переделываются, новые UI-тесты не пиши.
  Обновим их один раз, когда дизайн будет утверждён.
- Тесты базы и сохранения всегда должны оставаться рабочими.

Дополнение по итогам ревью плана: тесты базы лежат в том же `androidTest`,
что и тесты экранов, поэтому:
- на каждый коммит, кроме unit-тестов, — компиляция инструментальных тестов
  без запуска: `./gradlew compileDebugAndroidTestKotlin`;
- в тестах переделываемых экранов — только минимальные правки для компиляции;
  устаревшие проверки помечаются
  `@Ignore("Экран переделывается, обновим в коммите 39")`, но не удаляются.

## Команды

- Unit-тесты: `./gradlew testDebugUnitTest`
- Компиляция инструментальных тестов: `./gradlew compileDebugAndroidTestKotlin`
- Отладочная сборка: `./gradlew :app:assembleDebug`
- Установка на телефон (только по просьбе): `./gradlew :app:installDebug`
